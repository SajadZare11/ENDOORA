# دستورالعمل‌های عملیاتی مدیریت بحران و ران‌بوک‌های مهار اختلال (OPS-009)
## Incident Response Runbooks & Disaster Triage Protocols

این سند، مرجع جامع و استاندارد تیم‌های مهندسی زیرساخت، قابلیت اطمینان سایت (SRE) و پشتیبانی ارشد پلتفرم **ایندورا (Endoora)** برای شناسایی، تریاژ، مهار بلادرنگ و تحلیل پس از بحران (Post-Mortem) در رخدادهای با اولویت بالا و بحرانی است.

---

## ۱. دسته‌بندی شدت بحران و توافق‌نامه سطح خدمت (Severity & SLAs)

| اولویت | عنوان | تعریف و شواهد | حداکثر زمان پذیرش (Ack) | حداکثر زمان مهار (TTM) | حداکثر زمان رفع قطعی (TTR) |
|---|---|---|---|---|---|
| **P1 - بحرانی** | Critical Outage | قطعی کامل سرویس، از دست رفتن پایگاه‌داده اصلی، نقص داده یا توقف سراسری ثبت‌نام و تراکنش‌ها | **< ۵ دقیقه** | **< ۱۵ دقیقه** | **< ۳۰ دقیقه** |
| **P2 - بالا** | High Degraded | اختلال در درگاه پرداخت شاپرک، قطع سرویس تبدیل صوت/هوش مصنوعی، یا کاهش محسوس کارایی (>۳۰٪ کاربران) | **< ۱۵ دقیقه** | **< ۳۰ دقیقه** | **< ۶۰ دقیقه** |
| **P3 - متوسط** | Medium Issue | کندی موضعی در جستجوی پیشرفته، تأخیر در همگام‌سازی پیش‌نویس‌ها، یا خطای غیراصلی بدون توقف فرآیند یادگیری | **< ۱ ساعت** | **< ۴ ساعت** | **< ۲۴ ساعت** |
| **P4 - جزئی** | Low / Cosmetic | باگ‌های ظاهری جزئی، خطاهای نگارشی، یا درخواست‌های بهینه‌سازی غیرفوری | **< ۴ ساعت** | - | **اسپرینت بعد** |

---

## ۲. ساختار فرماندهی و نقش‌های اتاق بحران (Incident Command Hierarchy)

1. **فرمانده بحران (Incident Commander - IC):**
   - دارای اختیارات کامل جهت تصمیم‌گیری‌های حساس فنی (نظیر ارتقاء رپلیکا به سرور اصلی یا فعال‌سازی Maintenance Mode).
   - مسئول هماهنگی تیم‌های مهندسی و نظارت بر رعایت زمان‌بندی‌های SLA.
2. **مسئول ارتباطات و اطلاع‌رسانی (Communications Lead - CL):**
   - به‌روزرسانی صفحه وضعیت عمومی (`/status`) و اطلاع‌رسانی به کاربران، اساتید و پشتیبانی مشتریان.
3. **مهندسان عملیات و متخصصین دامنه (SRE / Domain Leads):**
   - اجرای دقیق دستورات و مراحل فنی ران‌بوک مربوطه به همراه ثبت لاگ‌ها و مستندات اعتبارسنجی.

---

## ۳. کاتالوگ ران‌بوک‌های ۶ گانه استاندارد عملیاتی

### ران‌بوک ۱: بازیابی و انتقال به پایگاه‌داده پشتیبان (`db-failover-recovery`)
- **شناسه رخداد:** P1_CRITICAL
- **سرویس متأثر:** PostgreSQL Primary Cluster
- **گام‌های اجرا:**
  1. **فعال‌سازی حالت نگهداری و قطع تراکنش‌های نوشتاری:**
     ```bash
     python manage.py set_maintenance_mode --readonly
     ```
     *اعتبارسنجی:* بازگشت پاسخ ۵۰۳ دوستانه به کاربران و قطع ورود داده‌های ناپایدار.
  2. **بررسی تأخیر رونوشت (Replication Lag):**
     ```sql
     SELECT now() - pg_last_xact_replay_timestamp() AS replication_lag;
     ```
     *اعتبارسنجی:* اطمینان از تاخیر کمتر از ۱۵ ثانیه پیش از آغاز فرآیند پروموشن.
  3. **ارتقاء سرور استندبای به سرور اصلی (Promote to Primary):**
     ```bash
     pg_ctl promote -D /var/lib/postgresql/data
     ```
     *اعتبارسنجی:* خروج پایگاه داده از حالت `read_only` و توانایی انجام تراکنش‌های Write.
  4. **تغییر آدرس اتصال اپلیکیشن و بازیابی ترافیک:**
     ```bash
     kubectl set env deployment/endoora-api ENDOORA_DB_HOST=pg-standby-01.internal
     ```
     *اعتبارسنجی:* بررسی وضعیت پروب‌های سلامت در `/api/health/` و خروج از حالت نگهداری.

---

### ران‌بوک ۲: مهار اختلال درگاه پرداخت بانکی (`payment-gateway-outage`)
- **شناسه رخداد:** P2_HIGH
- **سرویس متأثر:** Billing & Escrow Subsystem
- **گام‌های اجرا:**
  1. **بررسی نرخ خطای تراکنش‌ها:**
     ```bash
     python manage.py check_psp_health --provider=zarinpal
     ```
     *اعتبارسنجی:* افزایش نرخ عدم موفقیت تراکنش‌ها به بالای ۳۰٪ در بازه زمانی ۵ دقیقه‌ای.
  2. **تغییر مسیر خودکار ترافیک پرداخت به درگاه پشتیبان (سامان کیش):**
     ```bash
     python manage.py switch_payment_gateway --target=saman --drain-current
     ```
     *اعتبارسنجی:* اجرای موفق تراکنش آزمایشی ۱,۰۰۰ ریالی بر روی درگاه پشتیبان.
  3. **تمدید زمان رزروهای معلق اساتید:**
     ```bash
     python manage.py extend_pending_reservations_window --add-minutes=30
     ```
     *اعتبارسنجی:* جلوگیری از آزادسازی ناخواسته اسلات‌های رزرو شده کلاس‌های زبان‌آموزان.

---

### ران‌بوک ۳: مهار سهمیه و خطای ۴۲۹ هوش مصنوعی (`ai-quota-exhaustion`)
- **شناسه رخداد:** P2_HIGH
- **سرویس متأثر:** AI Gateway & Voice Lab
- **گام‌های اجرا:**
  1. **بررسی وضعیت مصرف سهمیه توکن و خطاهای ۴۲۹:**
     ```bash
     python manage.py inspect_ai_gateway_metrics --time-window=15m
     ```
     *اعتبارسنجی:* تأیید رخداد خطای `QUOTA_EXCEEDED` در ارائه‌دهنده فعال ابری.
  2. **چرخش کلید API یا سوئیچ به مدل محلی:**
     ```bash
     python manage.py rotate_ai_upstream_key --provider=gemini --fallback-to-local
     ```
     *اعتبارسنجی:* کاهش زمان پاسخ‌دهی پردازش تلفظ به کمتر از ۸۰۰ میلی‌ثانیه.
  3. **تشدید سیاست‌های کشینگ پاسخ‌های هوش مصنوعی:**
     ```bash
     python manage.py set_ai_caching_aggressiveness --level=high
     ```
     *اعتبارسنجی:* کاهش ۶۰ درصدی ارسال پرامپت‌های تکراری گرامر و ارزیابی نوشتاری.

---

### ران‌بوک ۴: مقابله با حملات ورود انبوه و تزریق اعتبار (`auth-credential-stuffing`)
- **شناسه رخداد:** P2_HIGH
- **سرویس متأثر:** Authentication & Security Module
- **گام‌های اجرا:**
  1. **شناسایی آدرس‌های IP مهاجم و توزیع درخواست‌ها:**
     ```bash
     python manage.py inspect_failed_logins --threshold=50 --window=5m
     ```
     *اعتبارسنجی:* استخراج الگوهای غیرعادی در مسیر `/api/accounts/login/`.
  2. **اعمال چالش امنیتی سخت‌گیرانه در لبه شبکه:**
     ```bash
     python manage.py enforce_strict_login_challenge --duration-hours=6
     ```
     *اعتبارسنجی:* افت ۹۵ درصدی خطاهای ۴۰۱ بدون مسدودسازی کاربران واقعی.
  3. **اعلان امنیتی به حساب‌های در معرض تهدید:**
     ```bash
     python manage.py notify_suspicious_login_targets --dry-run=false
     ```
     *اعتبارسنجی:* ثبت رویدادهای ممیزی تغییر رمز عبور و انقضای نشست‌های مشکوک.

---

### ران‌بوک ۵: قطعی فضای ذخیره‌سازی ابری فایل‌های صوتی (`storage-unavailability`)
- **شناسه رخداد:** P2_HIGH
- **سرویس متأثر:** Object Storage & Voice Lab
- **گام‌های اجرا:**
  1. **آزمون برقراری ارتباط با باکت اصلی:**
     ```bash
     python manage.py test_storage_connectivity --bucket=voice-recordings
     ```
     *اعتبارسنجی:* مشاهده خطاهای ۵۰۰ یا قطعی اتصال شبکه با کلاستر ذخیره‌سازی اولیه.
  2. **تغییر مسیر به باکت پشتیبان چندمنطقه‌ای:**
     ```bash
     python manage.py switch_storage_backend --target=backup-s3
     ```
     *اعتبارسنجی:* آپلود موفق فایل صوتی آزمایشی و دریافت URL با دسترسی موقت امن.
  3. **فعال‌سازی فرآیند همگام‌سازی در پس‌زمینه:**
     ```bash
     python manage.py sync_pending_audio_uploads --background
     ```
     *اعتبارسنجی:* تسویه کامل صف‌های ذخیره‌سازی بدون از دست رفتن فایل‌های ارسالی کاربران.

---

### ران‌بوک ۶: مهار حملات تکذیب سرویس و جهش ناگهانی ترافیک (`ddos-rate-limiting`)
- **شناسه رخداد:** P1_CRITICAL
- **سرویس متأثر:** Edge Gateway & Web Cluster
- **گام‌های اجرا:**
  1. **فعال‌سازی حالت حفاظت شدید لایه CDN:**
     ```bash
     python manage.py set_edge_under_attack_mode --enabled=true
     ```
     *اعتبارسنجی:* فیلتر درخواست‌های آلوده و اعمال چالش جاوااسکریپتی در لبه شبکه.
  2. **فعال‌سازی سراسری حالت کم‌مصرف (Global Low-Bandwidth Mode):**
     ```bash
     python manage.py set_global_low_bandwidth_flag --enabled=true
     ```
     *اعتبارسنجی:* کاهش ۸۰ درصدی ترافیک مصرفی سرور و بهینه‌سازی بار پردازشی.
  3. **افزایش پویای تعداد نودهای کلاستر وب (Autoscaling):**
     ```bash
     kubectl scale deployment/endoora-api --replicas=8
     ```
     *اعتبارسنجی:* بازگشت استفاده از پردازنده به کمتر از ۶۵٪ در تمامی پادها.

## ۴. چارچوب تحلیل پس از بحران و گزارش ریشه‌یابی (Post-Mortem & RCA Protocol)

پس از مهار و رفع هر رخداد با اولویت P1 یا P2، ظرف حداکثر **۴۸ ساعت** باید جلسه تحلیل علل ریشه‌ای (Blameless Post-Mortem) تشکیل شده و گزارش با ساختار زیر ثبت گردد:

1. **خلاصه رخداد و اثر تجاری:** مدت زمان قطعی، تعداد کاربران تحت تأثیر و خسارت بالقوه مالی.
2. **خط زمانی دقیق (Timeline):** از لحظه وقوع، زمان شناسایی توسط مانیتورینگ، آغاز مداخله و اعلام رفع نهایی.
3. **تحلیل ۵ چرا (5-Whys Analysis):** ریشه‌یابی علل پایه‌ای بدون سرزنش اشخاص.
4. **اقدامات اصلاحی و پیشگیرانه (Action Items):** تعریف وظایف مشخص با زمان‌بندی دقیق در تسک‌های اسپرینت بعدی.
